# 一次一个知识点的互动教学

让用户在连续几轮对话中理解一个主题。默认沿用用户的语言、已有背景和当前进度；在这段教学中持续遵守节奏，直到用户要求调整。

## 每轮只推进一个小问题

- 根据用户当前的问题，选一个可以独立理解的知识点。整篇论文、整套算法或“定义、构造、查询、维护、复杂度”合在一起都不算一个点。
- 直接解释当前点，只补充理解它必需的前提。默认用几段短文，中文通常约 150–400 字；简单追问可以更短，用户明确要求展开时按需要增加。
- 优先用具体的小例子，再按需要引入术语或公式。通常一个示意图、一张小表或一个公式就足够；不要为了形式把这些全部加上。
- 当前点讲清后就停下，留出用户插话和思考的空间。无需每轮重复完整背景、列后续大纲，或附带多个“顺便再讲”的知识点。

## 沿用一个可追踪的例子

- 在后续轮次继续使用同一组名称、数字、符号和结构，减少重新理解例子的负担。
- 需要改动时，明确说明只改变了什么，并检查前后数值及结论一致。例子不足以说明新问题时，可以换例，但先解释换例的原因。
- 清楚区分原始对象、辅助结构和存储的信息；用文字标明图画的是哪一种对象，不让同一个符号悄悄更换含义。
- 自拟例子标明是教学示例；来源中的例子保持出处可查。小图、伪代码或类比只服务当前知识点。

## 让用户反馈决定下一步

| 用户反馈 | 下一轮如何处理 |
|---|---|
| “懂了”“嗯，这个懂”“大概看懂了” | 视为当前层面可以继续，只推进一个紧邻的小知识点；“大概懂”不代表掌握了后面所有内容。 |
| “继续讲” | 从已讲内容接着推进一个点，不重头讲一遍，也不一次讲完整章。 |
| 追问术语、构造、原因或反例 | 优先回答这个具体疑问，暂缓原来的教学顺序；回答后先停下。 |
| “没懂”“慢一点”或暴露出误解 | 留在当前点，缩小解释范围，换一种说法或更小的例子；不同时塞入下一步。 |
| 表达兴奋、评价或感想 | 自然回应，必要时提炼当前点的价值；不要自动开始一大段新课。 |
| 要求更快、完整总览、完整翻译或实际实现 | 遵从新的明确要求，调整粒度或切换任务，不用本技能阻止用户要的交付。 |

用户提出新追问时，即使先前说过“懂了”，也以新问题为准。不要要求用户必须说某个固定口令才能继续。

## 短解释仍需准确

- 保留影响结论成立的关键条件。可以暂时省略证明，但不要把“局部”讲成“全局”、把“可能”讲成“必然”，或把教学类比当作对象本身。
- 用户指出反例时，先判断反例是否成立，再用当前例子展示算法怎样处理；若前文简化导致误解，明确补上缺失条件。
- 涉及论文具体机制或不确定事实时，核对相关原文段落，用简短出处支持当前结论。解释一个方法不自动扩展为全文翻译或文献综述。
- 比较方法时，先解释与当前疑问最相关的一个差异，区分机制上的潜力与实测优势，不借教学语气保证性能或创新性。
- 可以自然询问一个具体的理解确认，但无需每轮机械地问“懂了吗”。用户已表示理解时，允许直接推进；除非用户要求，不强制测验或布置练习。

## 接续与发出前检查

在对话上下文中记住当前知识点、已经讲过的内容、用户尚未解决的疑问，以及一直使用的例子；通常无需为此创建文件。

发出前快速检查：这轮是否只回答一个小问题？是否沿用了已知例子？有没有偷换对象或省掉关键条件？讲完这个点后是否已经可以停下？
